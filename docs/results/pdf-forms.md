# PDF forms (stream PARITY, check (e))

Proof: `tools/parity/guest/checks/pdfform.sh`, run nightly by `.github/workflows/parity.yml`. Evidence screenshots:
prerelease `parity-<run>` (`everyday-pdfform-*.png`).

## What is tested

A one-page form with two fill-in boxes (AcroForm text fields, generated by `tools/parity/guest/mkpdf.py form`) is opened the way
she opens a file: `gio open` (the file manager's path), which starts the default viewer. Real mouse clicks and key presses
(QMP, through the VM's USB tablet and keyboard) click the "Full name" box, type, click "City", type, then Save a copy
(Ctrl+S, a name, Enter). The saved file is read back and must contain both typed values (plain, UTF-16, hex or inside a
compressed object stream).

## Result on build 956af4a (Evince 46, the default viewer)

| step | result |
|---|---|
| form opens, boxes shown | pass (`pdfform.visible`) |
| fill two boxes, press Tab, Save a copy: both values in the file | pass (`pdfform.saved`) |
| fill two boxes and Save a copy straight away | the LAST box is lost (`pdfform.last-box` fails): Evince keeps a box once she leaves it. Tab, Enter, Esc and a click on another box all make it keep it. |

On Windows or a Mac a typed value is kept the moment it is typed. This is a known gap until the viewer decision (WP-56):
either accept Evince with a one-line hint, or Firefox's PDF viewer (pdf.js: `pdfjs.enableScripting` is locked off by policy, so
JavaScript forms would not calculate), or another viewer.
