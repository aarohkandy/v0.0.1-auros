## W01 [high (medium, medium)] Wayland CLIPBOARD is served to every X client at all times (no X-focus gate), so a background X app reads copied passwords
`src/aurwl/xclip.inc:222` · lens: privacy-security

**Scenario.** She copies a password in Firefox (Wayland). ddev_set_selection calls xw_selection_changed, then xc_publish, then xc_claim, so aurwl owns the X CLIPBOARD for window m->check. Any X client already running (Spotify, Discord, Zoom or VLC Flatpak with --socket=x11, or any compromised one) sends XConvertSelection(CLIPBOARD, TARGETS) and then UTF8_STRING, STRING or any offered mime. xc_serve (line 217) only checks `selection==CLIPBOARD && ds && m->clip_wl`. It never checks that an X window has keyboard focus, who the requestor is, or that a user gesture happened. wl_data_source_send_send makes Firefox write the secret into the pipe, and xfer_done writes it into a property of the requestor's window. XFixes also tells every X client the moment she copies something. The same happens at Xwayland start: xc_start (line 575) publishes whatever is already on the clipboard to a freshly launched X program. aurwl.c's own comments at ddev_set_selection (around 2538-2556) and selection_broadcast name this as the threat to avoid for Wayland: 'Copy a password ... and every running program could read it', and the offer goes only to the focused client. The X bridge bypasses that. The test enshrines the leak: tools/wltest-x-clip.inc clip_start (252-262) focuses a Wayland window, and sc_clip_text_wl_to_x (271) expects X requests to be served anyway. This is a code-reading finding; I did not run it.

**Fix.** At the top of xc_serve, after ds is known, refuse unless an X window has keyboard focus: `if (!c->focus || c->focus->role != ROLE_X11) { xc_notify(m, requestor, selection, target, 0, time); return; }`. This covers TARGETS and data. Preferably also release X ownership (x_set_selection_owner(m,0,CLIPBOARD), clip_wl=0) when focus leaves X and re-claim on X focus (hook in xw_focus), so X clients also cannot see copy timing or targets. Optionally do not publish a source that offers x-kde-passwordManagerHint. Change clip_start to focus an X window for the served scenarios, and add a scenario where a Wayland window is focused and the SelectionRequest must be answered with property None.

## W02 [high (high, high)] All X toplevels sit at root (0,0) and are never restacked, so Xwayland delivers her clicks to whichever X window was mapped last, not the one she is pointing at
`src/aurwl/xwm.inc:515` · lens: input-focus

**Scenario.** xwm_finish_manage (515) and the ConfigureRequest handler (746) force every managed X window to (0,0). x_configure (303) masks out XC_STACK, and a client's own raise request is dropped (the handler only forwards X/Y/W/H), so X stacking order is map order for the life of the session. Xwayland turns the wl_pointer enter/motion into root coordinates (focus window origin + surface-local point) and then hit-tests the X window tree. It does not use the Wayland focus surface. Every real-program run only clicked the newest window.

**Fix.** Add x_raise(): ConfigureWindow with mask XC_STACK (64) and value 0 (Above). Call it (1) in xwm_focus, (2) in xwm_configure when `activated` goes 0 to 1 (the argument is currently thrown away at 602), and (3) from aurwl_pointer_motion just before wl_pointer.enter whenever the entered root is ROLE_X11, with an xflush so the restack is written before the enter. The restack must also cover windows the shell hides: with (2) the active one is always X-top.

## W06 [medium (low)] Keystrokes typed into X programs (Discord/Spotify/Zoom logins, X terminals) reach the typed-word matcher; the password-field rules never apply to X
`src/aurwl/wishhook.c:183` · lens: privacy-security

**Scenario.** With wishes=on and a registered word such as 'doctor', she types a Discord or Spotify password, a Zoom passcode, or a sudo password in xterm. aurwl_key (aurwl.c:3928) calls wishhook_key for whatever window has focus. For an X window, textinput_state() is always TI_UNKNOWN, because Xwayland never binds text-input-v3 and textinput_focus finds no text input for that client. The app id is the X WM_CLASS ('discord', 'zoom', 'Spotify', 'xterm'), which is in neither NEVER_APPS nor BROWSER_APPS, and the title rarely contains a SECRET_TITLES word. So sensitive_now() reaches line 183 and returns 0, and every letter is buffered. A password or passphrase word that equals a trigger word is reported as `typed <word>` to the engine. This breaks docs/AI.md §3.5 and wishhook.h ('no matching in a field that says it holds a secret') for every X program. The Wayland path treats terminals and browsers as sensitive, but an X terminal or an Electron app on X is treated as an ordinary program. A fill_screen overlay fired mid-password also swallows the key that dismisses it. Only reachable when wishes is switched on.
