# AurOS security findings

Audit date 2026-10-23. Repository `aarohkandy/v0.0.1-auros`, branch `origin/main`. The audit was read-only and ran against several heads (9fea766, 29ea18c, 0643397, bcb8d89, eb4bf75, 6b66dcf, 05f3173 and others).

Line numbers drift between heads. Re-grep the symbol before editing.

Every finding below survived two independent skeptics, and severities were adjusted where a dispute was convincing. Duplicates across domains were merged.

---

## 1. Verdict

AurOS has a strong kernel and parser baseline: sysctls, firewall default-drop, `wr.c` single-writer discipline, a hardened answer channel, and fuzz-clean parsers. The weaknesses are above and around the kernel.

After skeptic review there are no critical findings. Both skeptics rated the two original criticals (installer image trust root, missing boot counting) high, and the disk-encryption finding high at most. There are eight high findings. They fall into five themes.

1. **The elevated installer trusts places a non-elevated process can write.** These are Downloads (bare-name child processes, DLL search order), `C:\AurOS` (the image and its manifest), and `%TEMP%` (the staging payloads). The baked image hash never reaches the staging side.
2. **Physical access means full access.**
   - The root is plain ext4. The LUKS and TPM code exists but is switched off.
   - Boot goes straight to an unauthenticated desktop.
   - GRUB has no lock and ships a root-shell entry.
3. **The publish chain is single-account trust.**
   - The apt signing key is a repository-level secret reachable from any branch.
   - Releases are mutable and several long jobs hold `contents: write`.
   - Main is unprotected.
   - A signed `auros-*` package is root on every machine by design.
4. **Recovery is thinner than the "never a black screen" promise.**
   - There is no boot counting, so a kernel that loads and then panics loops forever.
   - aurshell exits 0 on SIGTERM and is never restarted.
   - There is no watchdog and no display-loss recovery.
5. **The clock is wrong on every dual-boot PC.** There is no time daemon and Windows keeps the RTC in local time. In the Americas apt rejects Release files as "not valid yet", so security updates silently stop.

Two cross-cutting caveats shaped the severities.

- Most installer-side races need a same-user foothold, and UAC is not a security boundary. The installer is unsigned by design, so replacing `AurOS-Setup.exe` in Downloads is already a baseline attacker capability with an identical prompt. The installer TOCTOUs are therefore real, cheap defence in depth, but they do not dominate. The website's single-URL message and the Defender pre-clear (SEC-031) matter as much.
- Several gaps are already scheduled in the repo: WP-19 (restart card), WP-20 (display wait), WP-30 (boot counting), WP-53 (restore-kernel refresh), S4 (encryption and PIN), and stream BT (GRUB lock). Build these rather than re-specifying them. Where the audit's proposed control conflicted with a documented policy or enforced test, the control was corrected below. The main cases are `Automatic-Reboot "true"`, the Firefox DoH claims, the fwupd dbx claim, `--subset=verified`, and the `Requires=nftables.service` suggestion.

**Launch blockers (before strangers install):** SEC-001, 002, 003, 004, 005, 006, 007, 008, 014, 029.

## 3. Per-domain posture

**Windows installer.** Hashes are computed in the right places, WinHTTP keeps default certificate validation, and the gzip inflater and piece-list parser came through about 22M sanitizer-fuzzed iterations clean. Output size is capped and the PowerShell scripts interpolate only integers. The weakness is trust placement: the elevated exe runs from Downloads with no DLL or process-search hardening (SEC-002, 003), and the image, manifest and staging payloads sit in folders any local user can write (SEC-001, 009, 010). The installer is unsigned by design, so swapping the downloaded exe is a baseline capability. These controls are cheap defence in depth that removes the non-swap routes. They also pair with the website's one-URL message (SEC-031). Fixing SEC-001 even removes a 5 GB re-hash. The destructive fast path is not wired into the shipped wizard (SEC-057 is latent). Several original findings were dropped or reduced (section 7).

**Staging.** Parsers and write discipline are strong. `wr.c` is the single `O_RDWR` site with overflow-before-bounds and refuse-not-clamp. `build/staging` enforces the single-writer gate on preprocessed source. The GPT, NTFS, journal, image and rescue parsers are bounds-checked on reading. This is a code-review judgment, because sanitizer fuzzing was not completed. The journal pins destructive action to the live machine by serial, geometry and the full GPT hash. The staging initrd is an unauthenticated root payload that grub does not verify. That is a documented accepted gap under D7 (`THEFT.md:102,215-218`) and is mitigated by the TPM+PIN design once S4 ships. The rescue payload is unkeyed (SEC-033). The staging summary also flagged `written_unix==0` disabling the staleness traps (see section 3.12).

**Boot chain.** `bootchain` re-checks Authenticode, db/dbx, vendor dbx and SBAT itself, writes atomically and fails closed. Missing: boot counting (SEC-006), a GRUB lock (SEC-014), per-install root identity (SEC-019), and device-pinned lookups (SEC-034). Revocation is a documented decision, not a bug. fwupd is deliberately absent because a dbx write changes PCR 7 (BitLocker recovery and a broken sealed disk) and `bootchain` cannot stop a dbx write. SBAT arrives through shim and grub updates. Windows Update delivers dbx while Windows is kept (SEC-036). The restore kernel is frozen at install, tracked as WP-53 (SEC-035).

**Kernel and OS.** The sysctl and cmdline baseline is strong and enforced at build by `tools/hardentest.sh`. It covers kptr/dmesg restrict, BPF off, ptrace_scope=1, kexec off, `protected_*`, io_uring and userfaultfd off, `init_on_alloc`, `slab_nomerge` and `lockdown=integrity`. A real boot test (`tools/hardenboottest.sh`) boots the image under OVMF and probes the firewall from outside. Gaps: userns restriction not asserted (SEC-012), a stale module denylist (SEC-013), no restart prompt (SEC-028), and small hardening items (SEC-049 to 052). The raw audit's claim that every profile ships a public placeholder password on a sudo account is contradicted by later evidence: `build/forge:1462-1481` locks her and root's passwords and removes her from sudo, so it was not carried. Re-verify for the kiosk profile.

**Network.** Inbound is default-drop, cups-browsed is purged and build-checked, cupsd listens on localhost only, avahi publishes nothing, and there is no sshd or LLMNR. The big item is the clock (SEC-007). The rest is privacy and defence in depth (SEC-042 to 047, 060). Several raw "medium" claims did not hold: mode-2 DoH does not stop a rogue resolver, the CUPS grant is not remotely reachable, the Bluetooth page-scan claim is wrong, and the firewall has a booted test.

**Privilege.** The answer channel (`answer.sh` plus `src/aurfirst/request.c`) is well built: strict word allowlist, `O_NOFOLLOW`, regular-file and `nlink` checks, a clean environment, `NoNewPrivileges` and `ProtectSystem=strict`. Polkit rules are root-owned. No setuid binaries were added. The one surviving finding is the narrow Ferry confinement (SEC-058). Install and network grants are scoped to the user, which is the design. The gdebi pkexec grant has already been removed.

**C surface.** There is hot-spot hardening: aurwl clamps viewports, damage and surface counts and ties the clipboard to keyboard focus. `apps.c` refuses FIFOs and devices and split-execs. `notify.c` validates every D-Bus argument. `hivepeek` bounds-checks every read. Fuzzing found no memory errors (section 6). The one real defect is the unguarded config and font loaders (SEC-018, reproduced).

**Browser, scams, apps.** The Firefox policy is strong (HTTPS-only, locked Safe Browsing, uBlock force-installed, notifications and devtools blocked, checked by scamtest against Mozilla's schema). The scam-page escape works by design: native Wayland, no Xwayland, per-frame slot size so the "Close this" band is never covered, and crash-restore is off. This is untested in CI. Gaps are store curation (SEC-027), Flatpak override (SEC-015), add-ons (SEC-016), Downloads execution (SEC-017), and the lower items SEC-059 to 061. Flatpak runtimes are cleaned and updated by `auros-flatpak-update.timer` (contradicting the raw summary's "no update job").

**Updates and supply chain.** The AurOS apt channel (`build/aptchannel` plus `aptrepo.yml`) is well built and tested, and `-security` installs daily after a first-hour hold. Weak points: key custody and publish privileges (SEC-004, 005, 021), CI trust (SEC-020, 022, 038, 039), and freshness and reproducibility (SEC-040, 041). The key is root on every machine by design (`UPDATES.md:309`, `OWNER-SETUP.md:145`, `INCIDENTS.md:169`). The control is therefore protecting the key and the publish path, not a package guard. The channel serves only the desktop profile, which is deliberate for now (SEC-042).

**Theft and data.** The posture rests on S4, which is built and switched off (SEC-008, 029). One positive: swap is zram-only, with no disk swap or hibernation image, so there is no RAM copy to steal. Keep it that way when adding LUKS, and if a disk swap is ever needed, put it inside the LUKS container. The pieces are sequenced: encryption and the boot PIN first, then the wake lock screen, then GRUB lock, then optional erase.

**Reliability.** Section 4.

## 4. Reliability (never-BSOD) section

Already in place and unit-tested: `kernel.panic=10` plus `panic=10` on every entry, zram (50%, zstd) with earlyoom, journald caps (200M, 1G kept free), `fsck.repair=yes`, boot-time dpkg repair, atomic `grub.cfg` writes, `fallback` for kernels that fail to load, and a three-level safe mode for repeated desktop crashes (shell-guard, aursorry). The repo's own claim that "grub then starts the previous kernel if this one keeps failing" (`61-auros-reliability.conf`) is false for a kernel that loads and then panics.

Missing: nothing recovers from a bad kernel, a killed or hung shell, a lost display, a kernel lockup, or a GPU driver that cannot run. Build in this order. The dependencies matter, since automatic restarts and watchdog reboots are only safe once boot counting exists.
