# Session 2026-11-11: an OS for one person, and the first boots on the owner's Mac

The owner's two goals, in their words: (1) a custom OS for what a person needs, made by the
owner by hand for now; (2) later, people say what they want and get exactly that OS. This
session is about making (1) true. (2) is not started.

No physical PC has run AurOS. The owner has no spare laptop yet. Everything here is KVM on
homebase, QEMU on the owner's Mac (emulated, no acceleration), and CI.

## What is on `main` after this session

1. **Yesterday's batch, plus what three more reviews found.**
   - Start-up order: after a failed or ignored write the old order is put back and read again;
     "put back as it was" is said only when that is true. A 512-entry menu is left alone (the
     old loop dropped the last entry, which can be Windows Boot Manager).
   - A battery seen at the first power look and not at the second is a refusal.

2. **An installer for any profile.** `build/make-os PROFILE --base-url URL` goes profile, image,
   pieces, `AurOS-Setup-PROFILE.exe`. The profile is fixed when the installer is built. A new
   profile needs no C edit: the name is checked by one pattern (`[a-z0-9-]`, 1 to 32). A bad
   name is a build error, never desktop. With no profile named everything is as before (the
   generated headers are byte-identical).
   - The wizard used to write her look over the image's own. On a kiosk image that replaced the
     locked desktop with an ordinary one. A locked profile now gets no look page and keeps its
     look (`ab_profile_apply_look`, `tools/profilechoicestest.sh` with `OLD=1` shows the old
     result).
3. **`make-os.yml`.** Push `makeos/<profile>` or dispatch with `profile=`. It builds, runs four
   proofs on that image under KVM, publishes prerelease `os-<profile>-<sha7>`, then the real
   Windows journey on that exe. `workflowlint` rule 13 keeps it away from `latest`.
   `e2e.yml` takes a profile; what it expects and skips comes from the profile, and the summary
   says which steps ran.
4. **`docs/MAKE-AN-OS.md`**: the owner's page.
5. **Four defects found by using the published image on the Mac**, fixed and shown on that image
   under KVM with the new shell swapped in:
   - "This did not start" appeared after a flat 25 s while the program was still starting; the
     late window became a second entry and Close landed on the dead card. Now the shell asks
     whether the process is alive (`session_proc`), says "Still starting. This computer is
     taking a while.", gives a late window its own card, and a press on a dead card starts the
     program again.
   - Your files opened at `/`: programs started by the shell now begin in her home folder.
   - Her home had only Downloads: `rootfs/usr/lib/auros/home-folders` (forge, and
     `ExecStartPre` for homes that already exist).
   - "works like Like Windows".

## Decisions (agent, reversible)

| Decision | Why |
|---|---|
| One installer installs one profile, fixed at build time; no picker | "the owner makes each OS" |
| Profile names by pattern, not a list | a new profile is a file, not a code change |
| A locked profile gets no look page | the image's look is the product there |
| Recipe delivery (`DELIVERABLE_BASES`) stays desktop-only | a separate feature with its own evidence gate |
| "This did not start" only when the process is gone; 5 minutes for a launcher that handed off; never while alive | a slow computer is not a failed start |
| The HWE kernel (`agent/hwe`, `hwe-fix`: 7.0 beside 6.8) is NOT merged | it changes the kernel every PC starts; it wants its own release run |
| AurOS's own update channel stays desktop-only | see below |

## Open for the owner

- **Updates for a custom OS.** Ubuntu's fixes reach every profile daily. AurOS's own parts do
  not: `build/aptchannel` turns the channel off for every profile but desktop. The packages hold
  nothing a profile owns (policy, look, lockdown and account are generated files), so one shared
  channel would work; SEC-042 says each profile should have its own. Recommended: the shared
  channel, with a test that a kiosk is still a kiosk after an update. Until then a newer AurOS
  for her is a new installer.
- **Signing.** `docs/SIGNING.md` and `START-HERE.md` say D12 is "sign through SignPath, no
  date"; `docs/RELEASE.md` section 2 still says "not done, by decision". Nothing is signed.
- **Source code for an `os-*` prerelease: made, but not yet proved by a real run.** `make-os.yml`
  now has a `sources` job (it calls `sources.yml` with the profile) between `build` and `publish`:
  the release `sources-os-<profile>-<sha7>` is made from the image's own package list, published
  and re-downloaded and verified BEFORE the installer's release exists, and `publish` waits for
  it, so a run that cannot make the source offer publishes nothing. It adds about 1.5 hours.
  Three `os-*` prereleases made before this (`os-office-4d41b5b`, `os-office-850e90f`,
  `os-school-kiosk-b821bce`) have no source release and cannot get one (their runs kept no package
  list); do not send them to anyone. Push `makeos/office` once and check the release as
  `docs/MAKE-AN-OS.md` section 4 describes. Never delete a `sources-os-*` release either.
- **A kiosk beside Windows** logs in by itself as `student`. Fine for a school PC; decide before
  it goes on a person's own computer.
- Publish (`[publish N] [latest]`) is still the owner's push.
