## Goal

Fuzz every parser of untrusted input we wrote, under ASan+UBSan, fix every
crash with a regression test, then add hardening compiler flags to every C
build and prove them with a checksec-style test.

## Hardening (done, `f256364`)

- `build/cflags`: `HARDEN_CFLAGS` (forge), `HARDEN_STATIC` (`-static-pie`:
  staging init + aurscreen), `HARDEN_PE` (aurbridge .exe). Ferry's helpers
  carry the same line in `src/ferry/install.sh`.
- `tools/checksec.sh FILE...` is a gate in build/forge (8 binaries),
  build/staging (2) and build/aurbridge (2). `--selftest` proves every
  check fails on a binary built without its flag (ELF 7/7, static 5/5,
  PE 1/1). ssp/fortify cannot be read from a static binary (libc's copies
  are always there); stack-clash leaves no mark: both are said, not hidden.
- `.github/workflows/fuzz.yml`: regress.sh + checksec selftest on every
  push touching what they check (green on `f256364`).

## Proposal for A2: gpt.c accepts tables its own commit then damages (NOT applied)

`fuzz_gpt.c` plays `commit_table()` on a copy of the disk and checks that
none of its four writes lands inside a partition. Today's `gpt.c` accepts
two kinds of table (good CRCs, both copies agree) where it does:

| Reproducer (`tools/fuzz/pending/gpt/`) | The table | What commit_table() would do |
|---|---|---|
| `array-inside-windows` | primary header's entry array at LBA 20, inside the Windows partition (10..40) | write the new array into her NTFS |
| `partition-over-array` | 128 entries fill LBA 2-33; partition 1 starts at LBA 6 (before first_usable 34) | rewrite the table over the start of partition 1 |

Fix, ready to apply: `git apply tools/fuzz/pending/gpt/fix.diff` -- UEFI's
own header checks in `parse_header()` (MyLBA is where it was read;
first_usable >= 2, <= last_usable < disk; entry array on the disk and
outside the usable space) and, in `parse_entries()`, every used entry
inside [first_usable, last_usable]. Checked on homebase: both reproducers
pass with it; `tools/bridgetest.sh` 16/17 and `tools/gpttest.sh` 22/22
identical with and without it (the one failure is "no mingw" in that
container). After applying: `git mv tools/fuzz/pending/gpt/array-inside-windows
tools/fuzz/pending/gpt/partition-over-array tools/fuzz/regress/gpt/` (they
then run in fuzz.yml) and delete fix.diff. Risk if NOT applied: low in
practice (a real Windows disk does not look like this; commit's wr_arm()
window does not stop it), but it is "refuse first" on her disk.

Other A2 targets fuzzed clean: inflate.c (9 min, ~10M execs), journal.c
(5 min). A gpt backup-only table never reaches a commit (rescue_capture()
refuses it), so the harness does not commit one.

## Traps

- gcc's UBSan does not report the misaligned load clang's does: regress.sh
  uses clang when present.
- A regress file must fail the OLD code under the CURRENT harness: when a
  harness changes, re-derive its reproducers (finding 4's first reproducer
  was a harness artefact and was replaced).
- libwayland numbers globals in creation order; fuzz_aurwl assumes wl_shm
  is created just before wl_compositor (wl_display_init_shm first).
- Ubuntu's gcc already defaults to FORTIFY/SSP/PIE/CET; only `-z now` and
  `-static-pie` change anything there. The selftest builds the weak
  program with every flag explicitly turned off.
- `file` says "static-pie linked", not "statically linked": build/staging's
  check accepts both.
