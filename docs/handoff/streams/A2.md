## Goal

AurOS installs beside Windows in ~10 minutes and BitLocker PCs never
need decrypting. Today (the shipped, legacy path) the wizard downloads
the image to `C:\AurOS\`, arms BootNext, and after the restart the
staging initramfs (`src/aurstage/`) shrinks NTFS offline (ntfsresize),
copies the image, commits the GPT. BitLocker PCs must fully decrypt
first (hours). The fast path moves the shrink (Windows' own online
shrink, `Resize-Partition`) and the image write (raw, into the
unallocated gap only, fenced) into Windows during the download, so
staging only verifies and commits (~1 minute) and never touches NTFS.

Owner-approved, user-visible behaviours, all built: D10 (the Wi-Fi network she is on,
carried), D11 (BitLocker paused for two restarts, resumed on every abort path) and the SYSTEM
startup task that gives C: back its room -- and, new, the handover below.

**Rule: the wizard selects the fast path only once every step is proven green in simulation
AND on real Windows. The legacy path must keep working and its tests stay green.** The
`AB_CHOICE_*` macros in `phases.h` exist only under `AUROS_FASTPATH=1`; nothing selects the
fast path in the default build.

### The handover, in one paragraph

On a fast-path install (`choices.sh` records `via=gap`), Put Windows back no longer runs
`ferry back` into C:. `answer.sh` asks `ferry handover --need`, `handover.sh prepare` makes a
WRITTEN file of that size (+3% +16 MiB) in AurOS's root in one run of blocks on the disk, formats
it exFAT (label AUROSHANDOV) and attaches a loop device; `ferry back` fills it (R's layout,
docs/FERRY.md) and writes DONE last; `handover.sh finish` detaches it, hashes the file, finds its
address on the disk and PROVES it by reading the disk with O_DIRECT, and `answer.sh` arms the
restore with `auros_handover=FIRST,COUNT,SHA256` beside `next_entry`. grub hands that to THAT
restore only (`aurstage.handover=`). `rescue_restore` proves the blocks are inside AUROS-ROOT,
overlap nothing saved, begin as exFAT and hash to the record, then writes the saved table plus
AUROS-HANDOVER over exactly those blocks. At the next start of Windows the SYSTEM task
(`putback.ps1 -Mode system`) validates the manifest, hands the copy to a task that runs AS THE
USER (`-Mode user`, same file), re-hashes her copies, and only then removes the partition and grows
C:. **AurOS never writes into Windows; SYSTEM never writes into a profile; what AurOS left is
untrusted input** (docs/AURBRIDGE.md has the design and the tests).

**v1 limit:** the file must be one run of blocks on the disk; ext4 puts group metadata every
~1-2 GiB, so about that is the ceiling. Bigger collections get a plain refusal ("save them to a USB
stick first") and R's `ferry stick`. An encrypted AurOS root (S4) is refused the same way (the file
would be ciphertext). **v0.2:** a staging-side carve (shrink AUROS-ROOT offline, mkfs.exfat in the
tail, copy from a hard-link tree) lifts the limit; needs mkfs.exfat and the exfat module in the
staging initramfs. After the first real-Windows e2e passes (lead's decision).

## Traps hit

- `git fetch origin main` in a worktree of the lead's checkout updates only FETCH_HEAD: use
  `git fetch origin +main:refs/remotes/origin/main`. NEVER `git stash` in a worktree: the stash list is
  shared by every worktree and a pop took another stream's entry.
- Never `git checkout <path>` on a dirty tree to undo a test mutation (it reverted real edits once).
- PowerShell: **aliases beat functions** (`lp` is Out-Printer, so a helper called LP returned
  nothing, silently). A comma binds tighter than `+` (`@('a', 'b' + 'c', 1)` is not three
  elements). `$d = Get-Disk` taken before `Initialize-Disk` has no GUID. powershell.exe runs .NET
  with legacy path handling: use `\\?\` only for names over ~240 characters. A Windows checkout has
  CRLF; the exe is built from LF.
- GitHub keeps ONE pending run per concurrency group; fastpath.yml's path filter is narrow on purpose
  (another stream's push to some tools/*test.sh had been cancelling A2's runs).
- sgdisk/`mach_part` read whatever the main GPT header points at; at a torn instant ask `sgdisk -p`
  (it checks the CRC and falls back to the spare table, as the kernel does).
- ext4 lists a big file as several extents even when they follow each other; judge contiguity by
  each extent's start against the last one's end.
- Disk space on homebase: keep ~/work/auros/a2* small; traps on EXIT INT TERM in every test.
