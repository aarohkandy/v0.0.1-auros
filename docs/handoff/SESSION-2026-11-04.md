### Not fixed: too big, or cannot be shown from here (what to watch on a real PC)

1. **Put Windows back writes the saved EFI partition over the live one.** `rescue.c` (around 1594-1632) writes every megabyte that
   differs. AurOS never changes that partition, but **Windows does** if it runs after the install ("Windows" in the AurOS menu, or any
   Windows servicing). The restore then puts the install-time `bootmgfw.efi` and BCD back. Whether that breaks Windows (an older
   boot manager against Secure Boot revocations, a BCD out of step with C:) was not checked. A fix needs a FAT reader in staging, and
   nothing in `aurstage` parses FAT today. **Watch:** install, start Windows once from the AurOS menu, let it update, then Put
   Windows back: does Windows start with no recovery screen, and does it stay that way after the next update?
2. **A firmware reset or BIOS update that drops the AurOS entry cannot be repaired.** The keeper (S-24) only reorders an entry that
   exists. `BOOTX64.CSV`/`fbx64.efi` on AUROS-BOOT (`build/mkimage`) can recreate it only if the firmware boots that partition's
   removable path, which it will not while Windows Boot Manager is first. **Watch:** after "Load defaults" or a BIOS update, does the
   PC start Windows only? Is AurOS in the firmware boot menu as a disk entry, and does choosing it bring the entry back?
3. **The look-only run can say "ambiguous-windows" on NVMe.** `main.c` `find_windows` matches the journal's serial exactly; the real
   run uses `journal_disk`, which also takes punctuation-blind serials and the table hash (because Windows and Linux routinely
   disagree on NVMe serials). Any PC with a recovery partition then shows two Windows candidates in the dry run. Safe direction, and
   only the hardware-matrix line is wrong. **Watch:** `verdict=ambiguous-windows` in a dry run from an NVMe laptop.
4. **Hardware facts taken from memory or documentation, never from a machine:** Intel driver names (`iaStorVD`, `iaStorAC`, ...),
   "Optane" and "NVMe" model prefixes, AMD RAID model names; USB-C power-supply reporting in `health.c` (a laptop whose only mains
   input is a USB-C port); the Secured-core db judgement. **Watch:** a PC in "RAID On"/VMD mode must be refused in words before the
   download; a Surface or other Secured-core PC must be refused rather than reach a Secure Boot violation; a USB-C-only laptop on its
   charger must not be told it is on battery.
5. **Hibernation header (unverified suspicion).** `check_hiberfile` treats any non-zero first page other than a zeroed one as a live
   session. If Windows leaves a non-zero marker after resuming, a PC that was once hibernated and resumed would be refused for ever
   ("close it down properly"), and restarting would not clear it. The installer switches hibernation off first, which deletes the
   file, so this needs a vendor tool turning it back on. **Watch:** a refusal with `hibernated` on a PC whose Fast Startup and
   hibernation were both off before the install.
6. **Windows not started for a long time after Put Windows back, or the drive check interrupted.** The screen now warns; what
   happens if she holds the power button through the check is not tested. **Watch:** time the first start after a put-back on a large
   HDD.
