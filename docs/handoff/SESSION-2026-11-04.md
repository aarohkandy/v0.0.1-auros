What the two finished lanes found:

- **Fast-path twin**: the twin differs on every build only because the PE linker stamps the link
  time (`build/cflags` `HARDEN_PE` and `build/aurbridge-stub` `STUB_FLAGS` lack
  `-Wl,--no-insert-timestamp`; confirmed on homebase, mingw gcc 13 / binutils 2.41: the flag makes
  two links byte-identical). So it was never a different product. The lane deletes the twin step,
  the `e2e-fastpath` job and every consumer (build.yml, release.yml, e2e.yml, tools/e2e/*,
  releasegate.py, workflowlint.py, docs). `tools/e2e/selftest.py` passes on the new tree and gives 4
  FAILs on the old one. **Follow-up, not done:** add `-Wl,--no-insert-timestamp` to the wizard,
  console tool and stub links for reproducible `AurOS-Setup.exe` (changes shipped bytes; needs a
  release cycle).
- **Cinnamon**: (1) a real product race, not Cinnamon-specific. `auros-othersys-boot.service` and
  `auros-othersys-answer.service` both load/act/save `state.json` and start together when an answer
  is waiting. In confirm the boot unit was slow (first remove_iso + resize), the answer wrote
  Ubuntu-first, then boot's stale `hold()` put Windows first again and saved state without the
  answer. That explains the confirm and afteryes failures. Fixed in `cbadd44b` ("boot and answer
  take turns"). (2) The firstboot hang (stuck at `initrd-switch-root.service` for 1200 s, no output
  from the new root's systemd) looks like a one-off guest/KVM hang: the same disk booted in 66 s
  in confirm, and Cinnamon firstboot passed in runs 41538432102 and 41538963268. LightDM autologin
  works. Not fixed. If the next VM run hangs there again, it is real.
