### What the finished lanes found (full reports in `lane-reports.md`)

- **Fast-path twin** (`680658ed`): the twin differs on every build only because the PE linker
  stamps the link time into the header. `build/cflags` `HARDEN_PE` and `build/aurbridge-stub`
  `STUB_FLAGS` lack `-Wl,--no-insert-timestamp`. Confirmed on homebase (mingw gcc 13 / binutils
  2.41): with the flag, two links are byte-identical. So it was never a different product. The lane
  deletes the twin step, the `e2e-fastpath` job and every consumer: build.yml, release.yml,
  e2e.yml, tools/e2e/*, releasegate.py, workflowlint.py and the docs. `tools/e2e/selftest.py`
  passes on the new tree and gives 4 FAILs on the old one.
  Review findings, both minor, worth fixing on merge:
  - a stale comment near build.yml ~318 still mentions "the optional fast-path rebuild";
  - build.yml's default-is-fastpath grep is gone. Still covered by e2e.yml:165, e2e.py:468,
    `tools/customize/test_base_build.py:441` and check.mjs:920.

  **Follow-up, not done:** add `-Wl,--no-insert-timestamp` to the wizard, console tool and stub
  links, so `AurOS-Setup.exe` is reproducible. It changes shipped bytes, so it needs a release cycle.
- **Put-back wording** (`4a3fcf40`): the old wording was false for *both* install kinds. Before
  anything is armed, answer.sh copies the six folders (Desktop, Documents, Downloads, Music,
  Pictures, Videos) into `C:\Users\<her>\From AurOS`:
  - fast path (`via=gap` in `/etc/auros/installer-choices.conf`): handover.sh + putback.ps1;
  - legacy: ferry-back.

  If the copy cannot be done, nothing is removed and she is pointed to "Save my files to a USB
  stick first". Programs and settings are not carried. One wording is true for both kinds.
  Changed: settings.c, help `windows.html`, guide.html, install.html (claim
  `putback:carries-files`), helptest.py, check.mjs, windowspagetest.c, TRY-IT.md, streams/K.md.
  Tests:
  - helptest 50/0 with the fix, 2 fails without it;
  - windowspagetest 22/0 on homebase (does not build on macOS), 2 fails without the fix;
  - check.mjs syntax-checked only, not run in a browser: **run `node tools/site/check.mjs` before merging.**

  The 11-03 note said to land this after the BitLocker put-back is proven: the candidate's
  bitlocker e2e proves it.
- **Cinnamon** (`cbadd44b`): two findings.
  - A real product race, not specific to Cinnamon, **fixed**. `auros-othersys-boot.service` and
    `auros-othersys-answer.service` both load, act on and save `state.json`, and both start
    together when an answer is waiting. In confirm the boot unit was slow (its first remove_iso +
    resize). The answer wrote Ubuntu-first, then boot's stale `hold()` put Windows first again and
    saved state without the answer. That explains the confirm and afteryes failures.
  - The firstboot hang, **not fixed**. It sat at `initrd-switch-root.service` for 1200 s with no
    output from the new root's systemd. It looks like a one-off guest/KVM hang: the same disk
    booted in 66 s in confirm, and Cinnamon firstboot passed in runs 41538432102 and 41538963268.
    LightDM autologin works. If the next VM run hangs there again, treat it as real.
